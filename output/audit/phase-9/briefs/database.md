# Database and security audit

Output: `/Users/fahad/council/output/audit/phase-9/database.md`

Scope: every migration, test, seed and database-facing change that belongs to phase 9 (use `git log` and `git diff` against the commit before the phase started to separate it from earlier work), judged against the phase's Database work, the ADRs it cites, CONVENTIONS.md §3.2, §5, §6, §7 and the `supabase-database` skill. Start by reading `/Users/fahad/council/output/audit/phase-9/gates/GATES.md`.

1. **Migrations.** Read each new migration as if applying it to a fresh Supabase project: creation order, glossary table and column names (ADR-15), uuid primary keys, `tenant_id` on every tenant-owned table, composite `(id, tenant_id)` uniques and composite foreign keys for every reference to another tenant-owned table (ADR-20 rule 5), the all-branches representation (`branch_id NULL` + `all_branches` + partial unique index, never a sentinel UUID), money as `bigint` `_minor` columns (ADR-17), `timestamptz` and IANA zones (ADR-45), CHECK enums with canonical values, `updated_at` triggers, indexes on foreign keys and on RLS predicate columns. Confirm no migration that existed before the phase was edited (`git log --follow` on each file).
2. **RLS and grants.** For every table touched: RLS enabled, policies `TO authenticated`, `WITH CHECK` on insert and update, no `USING (true)` on tenant data, the branch-scoped template on branch-scoped tables, writes only where the ADR-28 allowlist permits them, explicit grants and revokes for `anon` and `authenticated` (Supabase grants broad defaults otherwise). Views must be `security_invoker` with explicit grants (ADR-21).
3. **Functions.** Every `SECURITY DEFINER` function pins `search_path`, checks scope internally with the helpers, has `EXECUTE` revoked from `public` and `anon` unless intended, and cannot be used to read or write another tenant's data. `has_tenant_role` must have no default on its branch parameter, and `has_tenant_role_any_branch` must pass only all-branches memberships.
4. **Attack it.** Against the running local stack, try to break isolation and record every attempt and its result: sign in as each seed user through `http://127.0.0.1:54321/auth/v1/token?grant_type=password`, then use the REST API (`/rest/v1/...`) and RPC endpoints to read and write other tenants' and other branches' rows, guess IDs, call privileged RPCs, write protected columns, insert rows whose foreign keys point into another tenant, and act after a membership is deactivated (deactivate it inside a `psql` transaction you roll back, or use pgTAP). Also try everything as `anon`. Do not leave changes behind.
5. **Tests.** Read the pgTAP files the phase added. Check that they cover the phase's Tests section and the matrix CONVENTIONS §7 requires: every table, operation (select, insert, update, delete), role (owner, branch manager of A, branch manager of B, receptionist, staff, outsider, anon), plus cross-tenant and cross-branch cases. List the uncovered cells. Flag tests that cannot fail (assertions that are vacuous, wrong expected error codes, fixtures that make the check trivially true).
6. **Types and seed.** Use the drift result from `GATES.md`. Check the seed loads only local demo data and that the documented seed logins work.
7. **Skill consistency.** Flag anything in the `supabase-database` skill or the glossary that now contradicts the real migrations, since future work will copy the skill.
