# Brief: Data model, multi-tenancy, and Django models (linker)

Output: {{COUNCIL_DIR}}/output/plan/data-model.md plus draft Django models in {{COUNCIL_DIR}}/output/plan/django/

1. Tenancy model: tenant (business), locations, memberships (user x tenant x role x location scope). How a request learns its tenant and location scope (session or JWT resolved to a membership on the server). What happens when a user belongs to several tenants. Every tenant-owned model uses one tenant-scoped manager; say what the base class looks like and what a forgotten manager would leak.
2. Schema for the MVP: every model with fields, types, constraints, indexes, and tenant/location keys. Cover tenants, locations, users, memberships, staff and staff-location assignments, programs (Apple pass style, rules, status), style-specific fields (store card rewards and thresholds, coupon offer, generic fields, and the columns event ticket and boarding pass will need so they are not a later rewrite), relevant locations on a program and on a pass, card design assets, enrollment links, customers (tenant-wide), passes (provider, style, external id, status, last pushed fields), the ledger (append-only events with idempotency keys; event kind depends on style), balances only where the style has a balance, audit log, settings.
3. Integrity, expressed as Django constraints and service rules: a customer balance cannot be updated except by a ledger event; two events with the same idempotency key cannot both apply (`UniqueConstraint`); a redeem cannot drive a stamp or points balance below zero (`CheckConstraint` plus a row lock in the service); a reward cannot be redeemed before its threshold is met; money, where a reward has a currency value, is `Decimal` with currency; time zones (`DateTimeField` stored in UTC + location tz); soft delete vs hard delete for customers and programs; ID strategy; `created_by`. Do not design appointment or double-booking constraints; this product has no calendar.
4. Permissions: the Django permission and queryset pattern for every model (tenant isolation + location scoping + role capabilities), and the pytest cases that prove a user of tenant A cannot read or write tenant B. Customer PII (email, phone, name) is tenant-scoped and not readable by a location-scoped role beyond what that role's job needs; state the rule.
5. Draft the models as Python in output/plan/django/ (one module per app: tenants, programs, customers, ledger, passes). They must be readable Django models a project can start from. Alongside them, note any `RunSQL` a migration needs because the ORM cannot express it. Do not write Supabase SQL, RLS policies, or `auth.uid()` helpers.
6. Diagrams: erDiagram of the MVP schema; a diagram of the request from JWT or session to tenant-scoped queryset; a state diagram for a pass and for a program.
7. Reporting: which basic analytics are ORM queries or database views, which indexes they need, and when (if ever) materialised views are needed.

Draft the skill `django-data`: apps and model layout, naming, required fields (`tenant`, timestamps, audit), the tenant manager, constraint patterns, how to add a new tenant-scoped model step by step, migrations, and the pytest that must accompany it.

Add your "Proposed decisions" section.
