# Loopy Loyalty parity, extra features and user journeys

Output: `{{COUNCIL_DIR}}/output/plan/final/drafts/parity.md`

1. Parity matrix. One row per Loopy Loyalty feature (walk every page, setting, report and flow in the evidence): Loopy feature and evidence reference; what it does for the business; our equivalent (module, phase.subphase); how ours differs or improves, and why; or "not planned" with the reason. Group by the areas the evidence actually has (programs and cards, customers, earn and redeem, passes, locations, staff, analytics, campaigns, settings, platform). End with coverage numbers per area.
2. Beyond Loopy Loyalty. Loopy is a stamp-card product. This product must also cover every Apple Wallet pass style and relevant locations on any pass; those are requirements from `briefs/plan/common.md`, not optional ideas. Then propose additional features that would make this product better for multi-location businesses in Kuwait and the GCC, and for selling to many companies. Consider for example: Arabic-first enrollment and Hijri dates, WhatsApp enrollment, location comparison, tiers, referrals, a public API, platform admin tooling (required in the MVP, because we create each account), audit log, data export, a rollback story for already-issued passes. For each: the problem it solves, who uses it, rough size, dependencies, and a proposed phase.subphase. Keep the MVP scope unchanged unless a feature is required for the first business to go live; say so explicitly if you think it is.
3. User journeys. For each role (platform admin, tenant owner, location manager, stamper, customer with a wallet pass) describe the key journeys step by step, naming the screens and the phase.subphase that delivers each step. Include a Mermaid user-journey or flowchart per role.
4. Residual issues found while doing the above.
